# 0028 — Stamp the project's version into the Claude Code plugin

Date: 2026-11-08
Status: accepted

## Context

Decision 0022 stamps `engine/VERSION` into the rendered plugin's
`.claude-plugin/plugin.json`. The engine version is the version of whichever CLI
runs the sync, not a property of the project. Every CLI release therefore changed
one generated byte in every project that renders the plugin, and `sync --check`
answered "sync needed" in a checkout whose sources, manifest and lock had not
moved. A host that upgrades the CLI on a timer showed the plugin's `Sync now`
band again after every upgrade, and a sync made it disappear only until the next
one.

Decision 0023 already settled that the version a project is on is the one its
manifest records, `schema_version`, and that only `intelligence update` moves it.
Nothing reads the plugin's `version`: the hooks module never consults it, and a
plugin loaded from the skills directory is not resolved through a marketplace.

## Decision

1. The plugin manifest's `version` is the project's `schema_version`, read
   from the manifest the sync renders. It supersedes the `version` clause of
   decision 0022 item 1 and that decision's "moves with `engine/VERSION`"
   consequence; the rest of 0022 stands.
2. The engine takes only a plain `X.Y.Z` for it. Any other value refuses the
   sync, naming the field, because the value is written into JSON.
3. `render_claude_plugin` takes the manifest as an optional second argument
   and defaults to the exported `CONFIG_FILE`, so a project's own `claude.sh`
   that calls it with the output directory alone keeps working.

## Consequences

- Upgrading the CLI changes no generated byte of the plugin. A new release can
  still change the plugin's hooks module, README or `hooks.json`; then the files
  differ for a real reason and "sync needed" is true.
- `intelligence update` moves the stamp and, through the sync it runs, the
  plugin's `version` in the same reviewed change.
- Two teammates on different CLIs of one major render the same plugin manifest
  for the same commit.

## Rejected

- **Omitting `version`.** It would also stop the noise, but the manifest would
  no longer say which Intelligence version the project renders, and the
  project's stamp already answers that without changing on a CLI upgrade.
- **A version of the template's own, bumped by hand.** A hand-maintained number
  is the step that gets forgotten, and the file contents already say whether
  the template changed.
- **Syncing every checkout after a CLI upgrade.** It rewrites output under work
  in progress and leaves the noisy diff in place.
